# Running the listener as a service (`rpi/user-service.sh`)

## Goal

Make `dankbot listen` an appliance: after a reboot the desk robot comes up on its
own — no login, no terminal — and can be started / restarted / stopped / watched
from one place. `rpi/user-service.sh` (the file in `rpi/` was a fixme stub)
installs and drives it as a **systemd user service**.

## Approach

One control script, one unit, one file of state:

| Path | What |
|---|---|
| `~/.config/systemd/user/dankbot-listen.service` | the unit (generated by the script) |
| `~/.config/dankbot/listen.env` | `DANKBOT_*` settings (commented template, written once) |
| *the journal* | the quips and the unit's own start/stop/exit events (see below) |

```sh
bash rpi/user-service.sh [install|start|stop|restart|enable|disable|status|logs|uninstall]
```

`install` (the default) writes the env template, writes the unit, `daemon-reload`s,
`enable --now`s it, and enables linger.

### Why a *user* unit

* It runs as the login user, so it inherits the `audio` / `plugdev` / `dialout`
  access `rpi/install-rpi.sh` grants that account — the mic and the touchy-pad are
  both ordinary-user devices.
* `loginctl enable-linger $USER` starts that user's manager at boot, so the
  service comes up with nobody logged in (this is the "autostart next boot"
  requirement).
* Everything else it needs is already per-user: the Moonshine model cache in
  `~/.cache/moonshine_voice`, the pad's udev rule (`OWNER=<uid>`).
* A *system* unit would have to run as a dedicated user and re-grant all of that.

### Logs: the journal, no file

`dankbot listen` logs to **stderr**, and the unit leaves both streams where systemd
puts them by default:

```ini
StandardOutput=journal
StandardError=inherit
```

Journald rather than a file, because of where this box is going:

* Raspberry Pi OS keeps **no `/var/log/journal`**, so journald stores in
  `/run/log/journal` — **tmpfs**. The quip log therefore costs no SD-card writes
  (which matters once the root filesystem is read-only) and needs no rotation
  rule: it is gone at reboot and **capped by journald itself** (`RuntimeMaxUse`,
  `journalctl --vacuum-*`), so it cannot grow without bound the way a plain
  appended file does.
* Losing it at reboot is fine — a log is wanted *during* a session, to see what the
  robot just said and why it restarted. Nothing here is worth an fsync to flash.
* The quips and the unit's own start/stop/exit events land in **one** stream, so
  `journalctl --user-unit=dankbot-listen -f` (what `user-service.sh logs` runs)
  answers both "what did it say?" and "why did it restart?".

`StandardError=inherit` (rather than a second `journal`) keeps one file
descriptor, so the two streams cannot interleave mid-line.

**The alternatives that were considered** (and the measurements behind the
choice):

| Destination | RAM-backed? | Growth | Why not |
|---|---|---|---|
| `~/.local/state/dankbot/listen.log` (the first cut) | no | unbounded; needs logrotate | writes to flash, and a read-only root breaks it outright |
| `/tmp/dankbot.log` | only if `/tmp` is tmpfs | same as journald if tmpfs | stock Raspberry Pi OS keeps `/tmp` on the **root ext4** (`tmp.mount` ships but is not enabled), so this is SD-card writes that survive a reboot; and under a plain read-only root with no tmpfs on `/tmp`, `StandardOutput=append:` **fails to open** → the unit fails at start and, with `Restart=on-failure`, loops every 5 s |
| `append:%t/dankbot.log` (`%t` = `$XDG_RUNTIME_DIR`, i.e. `/run/user/<uid>`) | yes, by construction | bounded by the boot | the best *file* option, and the fallback if a file is ever wanted — but it buys nothing over the journal and adds a path to manage |
| journald (**chosen**) | yes (volatile on RPi OS) | capped by journald | — |

Two findings worth keeping, from testing `%t` and `RuntimeDirectory=` against a
live user manager (systemd 257):

* `%t` **does** expand to `$XDG_RUNTIME_DIR` in a user unit's `StandardOutput=`,
  and `append:` there works (the file landed in `/run/user/1000/`).
* **`RuntimeDirectory=` does not give `StandardOutput=append:` its parent
  directory.** `RuntimeDirectory=foo` + `append:%t/foo/x.log` fails with
  `status=209/STDOUT … Failed to set up standard output: No such file or
  directory`, while a sibling probe showed the directory *is* created by the time
  `ExecStart` runs — stdio is opened **before** the runtime directory exists. So a
  subdirectory log path needs the parent to already exist (or a shell wrapper);
  and any `append:` path whose parent is missing at boot is a start failure, not a
  degraded log.

### Reading it back

`journalctl --user-unit=dankbot-listen -f` — `--user-unit=` matches the unit's
entries in the journal the system keeps, which is readable by group `adm` on
Debian/Raspberry Pi OS (the default Pi user is in `adm`). The per-user variant,
`journalctl --user -u dankbot-listen -f`, is the other documented form; it reads
the per-user journal file that journald ACLs to its owner, so it is the one to try
if `--user-unit` comes back empty.

### Settings: the env file, not flags in the unit

`EnvironmentFile=-~/.config/dankbot/listen.env` — the leading `-` makes the file
optional, so its absence just means the built-in defaults. Every `DANKBOT_*`
variable follows the CLI's existing flag → env → default rule, so the file is
pure override and the unit stays stable. One-off flags belong in the unit via
`systemctl --user edit dankbot-listen`.

### Keep trying

```ini
Restart=on-failure
RestartSec=5
```

A mic plugged in *after* boot is a hard `AudioError` (see
`docs/plans/micreconnect.md` — supervision only covers a *re*-open), and a local
`ollama serve` may still be loading its model. `on-failure` (not `always`) means
a `systemctl --user stop` stays stopped, while a boot-time failure retries until
the hardware or server appears. A user unit cannot order itself after the
*system* `ollama.service` (cross-manager ordering is ignored), so this is what
covers the not-yet-ready server.

### Finding the binary

`ExecStart` needs an absolute path (a user unit gets a minimal PATH). Resolution
order: `$DANKBOT_BIN` → `command -v dankbot` (pipx/pip) →
`<repo>/.venv/bin/dankbot` → `poetry env info --path` + `/bin/dankbot` (Poetry's
cache venv). The resolved path is baked into the unit, so **Poetry is not needed
at boot**.

`WorkingDirectory` is the repo root, so `--fake sim-overheard.txt` and a relative
`--persona-file` behave as they do under `just listen`.

## Layout

* `rpi/user-service.sh` — the script (bash, `set -euo pipefail`, `log()` / `die()`
  helpers in the style of `rpi/install-rpi.sh`).
* `docs/plans/rpi-service.md` — this file.
* `rpi/README.md` — the "Running as a service" section.

## Sequence

1. **install** — env template, unit, `daemon-reload`, `enable --now`, linger.
2. **day to day** — `status` / `logs` / `restart`; settings go in the env file.
3. **uninstall** — `disable --now`, remove the unit (the env file is kept, since it
   is the user's data; the journal entries age out on their own).

## Testing

* `bash -n rpi/user-service.sh` (syntax).
* A sandboxed run with stubbed `systemctl` / `loginctl` and a temporary `HOME`:
  the generated unit, every subcommand's exit code, the missing-binary error, the
  linger fallback, the "no user manager" path, and the **not-installed guard**
  every command now shares (`start` before `install` reports "is not installed —
  run: … install" rather than passing systemd's bare "Unit … not found" through).
* `systemd-analyze verify` on the generated unit (clean).
* A live run against the box's real user manager with a stub `dankbot` (and a
  stubbed `loginctl`, so real linger state was not touched): the unit came up
  `active (running)`, both stdout and stderr reached the **journal** (visible via
  `systemctl --user status` and `journalctl --user-unit=…`), and a
  `DANKBOT_*`-style line added to the env file reached the process after a
  restart — i.e. `EnvironmentFile` is wired.
* The `%t` / `RuntimeDirectory=` probes behind the log-destination table above
  (throwaway units, removed afterwards).

One caveat from that run: this devcontainer's journald is volatile (like a Pi's)
but has **no per-user journal file**, so `journalctl --user -u …` prints "No
journal files were found." while `journalctl --user-unit=…` shows everything —
which is why `logs` uses the latter.

There is no bash test harness in this repo (`just test` is pytest), so the script
is verified by hand. The Python suite is untouched by this change.

## Risks / open questions

* **Journal readability.** `logs` uses `journalctl --user-unit=`, which needs read
  access to the journal — the Pi's default user has it via `adm`. On an account
  without that (or a journald with `SplitMode=none` / no per-user file),
  `journalctl --user -u dankbot-listen -f` is the alternative; the script's header
  and `rpi/README.md` name it.
* **Volatile journal = no logs across a reboot.** Accepted deliberately (see
  above). If a persistent log is ever wanted, do *not* just point `StandardOutput=`
  at a file on flash: either make `/var/log/journal` exist (persistent journald,
  which caps itself) or add in-app rotation (`RotatingFileHandler` behind a
  `DANKBOT_LOG_FILE` setting, with the unit's streams left on the journal so
  nothing is written twice).
* **Linger is a privilege escalation.** `loginctl enable-linger $USER` may need
  polkit auth or `sudo`. The script tries the unprivileged path, then
  passwordless `sudo -n`, then prints the exact command — it never blocks on a
  password prompt.
* **Restart loop.** A permanent failure (wrong model, no server, no mic) retries
  every 5 s forever. That is intended for an appliance, but `status` reads
  `activating (auto-restart)`; `StartLimitBurst` is left at its default so
  systemd does not give up on it.
* **Not covered yet:** running the *display* alone, or a second instance per
  pad/mic pair (the unit name is fixed).
